# Candidate capture redaction contract v1

This document specifies an offline deterministic candidate transform over
synthetic captured projections. It does not authorize traffic recording,
persistence, retries, scheduling, deployment, packaging, or activation. A
finding is descriptive evidence only. Murmur hashes and claims are unrelated.

## Closed result

The transform accepts a context, optional declared wrapper, and either inline
bytes or a complete chunk manifest. It returns exactly one of:

- `unchanged`: output bytes equal the input projection and findings are empty;
- `transformed`: output bytes and ordered findings, where every finding is
  exactly `{rule_id, context}` and at least one replacement changed bytes;
- `rejected`: one code and no output, finding, digest, offset, snippet,
  diagnostic, or input-derived text.

The only rejection codes are `unknown_context`, `malformed_encoding`,
`unsupported_envelope`, `artifact_unavailable`, `limit_exceeded`, and
`invalid_chunks`. Unknown contexts use `unknown_context`. Bad declared syntax
or wrapper data uses `malformed_encoding`. An unknown wrapper or envelope
schema/version/encoding uses `unsupported_envelope`. Any artifact-backed input
uses `artifact_unavailable`; this contract has no resolver. Resource excess is
`limit_exceeded`. Incomplete, misordered, incorrectly sized, or
integrity-invalid chunks use `invalid_chunks`.

Replace each sensitive scalar with the ASCII bytes
`[REDACTED:<rule_id>]`. A sensitive header replaces its whole value. A
sensitive structured key applies to every scalar below that value. Values with
an ASCII-case-insensitive `Basic ` or `Bearer ` prefix and scalar values
containing a syntactically valid ASCII email address are replaced whole. URL
userinfo is replaced whole. There is no value-derived token or equality
pseudonym.

## Registry and matching

`privacy_registry.json` is generated only from constants in
`tools/generate_privacy.py`; `--check` compares exact generated bytes. The
closed contexts are `headers`, `url`, `json`, `form`, and
`extension_envelope`; the only wrappers are `percent` and `base64`.

For sensitive-key matching, ASCII uppercase becomes lowercase, then every run
of `-`, `_`, `.`, or ASCII whitespace (space, tab, LF, VT, FF, and CR) becomes
exactly one `-`. Leading and trailing runs are retained as one leading or
trailing `-`; they are never stripped. No heuristic word splitting occurs.
Consequently camel-case spellings are present explicitly in the registry after
ASCII lowercasing, including `apikey`, `accesstoken`, and `secretaccesskey`.
Registry rule order is normative: credential headers, cookies, secret keys,
credential schemes, emails, then URL userinfo. Direct key rules take
precedence over value rules.

Findings follow input header/form/query order. URL userinfo precedes query
findings. JSON uses depth-first traversal with object keys in Unicode
code-point order and arrays in input order. An envelope emits metadata
findings in input order, followed by inline-payload findings. Duplicate
findings are retained because each denotes a distinct replacement.

## One decode and canonical output

The encoded projection is checked before decoding. If a wrapper is declared,
decode it exactly once, then decode the context exactly once. Percent syntax
requires complete two-hex-digit escapes; its canonical form uses uppercase
hex and leaves only RFC 3986 unreserved bytes literal. Base64 is padded RFC
4648 standard base64. Transformed output is re-encoded with the declared
wrapper. There is no heuristic or recursive decoding, decompression, archive
handling, charset detection, descriptor discovery, or generic protobuf
parsing.

Supported context syntax and emission are:

- Headers are UTF-8 lines `name: value\n`, split at the first `: ` only. A
  nonempty name contains only printable ASCII other than `:`. Names, order,
  the single-space separator, and any later colons in the value are preserved;
  values alone are replaced.
- A URL is an absolute `http` or `https` URL without a fragment. Scheme, host,
  port, and path are preserved. Userinfo is emitted as one percent-encoded
  replacement. Query pairs retain order and use exactly one `=` each; decoded
  names and values are emitted with the canonical percent rule above.
- JSON is strict UTF-8 JSON with one complete value, no duplicate object keys,
  and no non-finite number. Before constructing a JSON tree, a bounded
  token-level pass enforces depth, rejects duplicate decoded key spellings,
  and validates string escapes. A high-surrogate escape must be immediately
  followed by a low-surrogate escape; lone high or low surrogates reject as
  `malformed_encoding`. Excessive depth rejects as `limit_exceeded` without
  recursive materialization. Objects emit with keys sorted by Unicode code
  point, arrays retain order, and strings deterministically escape control
  bytes, quote, and backslash. All other valid Unicode scalars—including
  U+2028 and U+2029—emit as literal UTF-8 rather than ASCII escapes. There is
  no insignificant whitespace or final newline.
- Form data is zero or more ordered `name=value` fields separated by `&`.
  Names and values use the canonical percent rule; `+` is literal rather than
  an alternate space spelling.
- `ExtensionEnvelope` is the frozen JSON projection of the registry entry
  `jobseek.synthetic.capture`, version `1`, encoding `canonical_json`. Its
  outer keys are exactly `schema_id`, `schema_version`, `encoding`,
  `payload_b64`, and `payload_sha256`. The canonical-JSON payload contains an
  ordered `metadata` header list and exactly one `inline` object with a closed
  non-envelope context and `data_b64`. The inline payload is scanned once.
  The pre-existing `payload_sha256` is never computed or compared and is
  cleared to the empty string in safe normalized output. An `artifact` member
  rejects as unavailable; unknown schema/version/encoding rejects as
  unsupported.

An accepted input without findings must already have the emitted byte form;
otherwise it rejects as `malformed_encoding`. This keeps `unchanged` literal
and prevents unreported normalization.

## Limits and chunks

All maxima are inclusive:

| Bound | Maximum |
| --- | ---: |
| Encoded input | 1,048,576 bytes |
| Chunks | 256 |
| Decoded working set | 2,097,152 bytes |
| Output | 2,097,152 bytes |
| JSON depth | 32 |
| Aggregate headers, form fields, or JSON nodes | 10,000 |

Known declared sizes/counts are checked before materialization. Chunk count
and total declared size are checked first. A complete manifest must then have
contiguous zero-based sequence numbers, exact declared sizes, and lowercase
SHA-256 integrity values matching every wholly synthetic inline fixture
chunk. Only after every check passes are chunks joined in order, allowing a
match across any chunk boundary. Chunk integrity values are fixture evidence
only: they are not emitted, persisted, or used as redaction pseudonyms.

The 1 MiB ingress ceiling and non-expanding single wrapper decode dominate the
2 MiB decoded-working-set and output ceilings for current valid projections.
The corpus therefore exercises the reachable encoded/chunk/depth/count bounds
end to end and exercises both dominated comparators directly at maximum minus
one, maximum, and maximum plus one. This defense-in-depth statement does not
relax either 2 MiB bound.

## Synthetic conformance digest

The pure transform never returns a digest. Each synthetic manifest case may
carry `result_digest` as conformance evidence only. It is SHA-256 over the UTF-8
domain `jobseek.runtime.v1.redaction.result\0` (one NUL) followed immediately
by canonical UTF-8 JSON of the safe expected result. An accepted safe object
contains exactly `case_id`, `status`, ordered `findings`, and padded standard
`output_b64`. A rejected safe object contains exactly `case_id`, `status`, and
`error_code`—never input, output, or findings.

Digest JSON recursively sorts object keys by Unicode code-point order,
retains array order, disables ASCII escaping, emits no insignificant
whitespace, and has no trailing newline. Raw or rejected input bytes are never
hashed. Python and Go independently hard-code the complete mandatory case-ID
set and must match every safe expected result and conformance digest exactly.
